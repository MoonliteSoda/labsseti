# Подготовка стенда и проверка ЛР №2

Команды ниже выполняются на двух Orange Pi 5 с Raspberry Pi 3B между ними. Подставьте фактические IPv4-адреса, интерфейс Ethernet и путь к эталонному видео. Настройка адресов/маршрутов должна соответствовать стенду кафедры.

## До запуска

На обоих Orange Pi и на Raspberry Pi зафиксируйте `ip -br addr`, `ip route` и MTU Ethernet-интерфейса (`ip link show`). С передатчика проверьте `ping -c 3 <IP_ПРИЁМНИКА>` и `traceroute <IP_ПРИЁМНИКА>`; в маршруте должен присутствовать Raspberry Pi. Проверьте, что UDP-порт 5000 доступен и не используется другим процессом.

На обоих Orange Pi нужны Linux, установленный в системе Python 3.14 или новее и FFmpeg. На передатчике FFmpeg должен поддерживать кодирование `libx264`, на приёмнике — декодирование H.264. Сторонние Python-библиотеки для ЛР-2 не нужны: в `pyproject.toml` список зависимостей пуст. `uv`, `pip` и виртуальное окружение для этого сценария не требуются.

Для измерений подготовьте `ip` (`iproute2`), `ping`, `traceroute`, `tcpdump` и `sha256sum` (`coreutils`). `ffprobe` нужен для проверки числа кадров; `tshark` из набора Wireshark нужен для автоматической сводки захвата, но запуску видеопередачи не требуется. Перед опытом на каждом Orange Pi проверьте:

```sh
python3 --version
ffmpeg -version
ffprobe -version
```

На передатчике проверьте кодировщик командой `ffmpeg -hide_banner -encoders | grep libx264`. Также убедитесь, что приёмник имеет достаточно места для выходного H.264-файла: пятиминутный поток может занимать сотни мегабайт.

Скопируйте проект на оба Orange Pi. В **каждом новом терминале**, из которого запускается Python-программа, перейдите в корень проекта и задайте путь к пакету `labs`:

```sh
cd /путь/к/PythonProject
export PYTHONPATH="$PWD/src${PYTHONPATH:+:$PYTHONPATH}"
python3 -m unittest discover -s tests -v
```

Проверьте, что `python3 --version` показывает 3.14 или новее. `PYTHONPATH` задаётся для текущего терминала и не изменяет системную установку Python. Команды ниже запускаются в терминале, где уже выполнены `cd` и `export`.

Для проверки видеорежима нужен эталонный файл, который FFmpeg умеет читать. Выберите ролик продолжительностью хотя бы несколько десятков секунд: при частом повторе очень короткого файла фактическая средняя частота может отличаться от заданных 25 FPS. Итоговую частоту измеряйте по отчёту. Текущая команда отправителя рассчитана прежде всего на файл; параметры конкретной USB-камеры необходимо определить на стенде.

## Сначала проверьте двоичный файл

На приёмнике запустите:

```sh
python3 -m labs.lab2.receiver --host 0.0.0.0 --port 5001 --output restored.bin
```

На передатчике:

```sh
python3 -m labs.lab2.filecheck <IP_ПРИЁМНИКА> source.bin --port 5001
```

После сообщения `transfer complete` сравните `sha256sum source.bin` на передатчике и `sha256sum restored.bin` на приёмнике. Файловый режим использует подтверждения и повторы; при исчерпании лимита повторов отправитель сообщит об ошибке. Для нового опыта перезапустите приёмник: он открывает выходной файл заново.

## Пятиминутный видеопрогон

На приёмнике в первом терминале начните захват пакетов на фактическом Ethernet-интерфейсе:

```sh
sudo tcpdump -ni <ИНТЕРФЕЙС> -s 0 -w lab2.pcap 'udp port 5000 or (ip[6:2] & 0x3fff != 0)'
```

Во втором терминале приёмника запустите программу на переднем плане:

```sh
python3 -m labs.lab2.receiver --host 0.0.0.0 --port 5000 --output received.h264 --decode > receiver.log 2>&1
```

В третьем терминале приёмника найдите PID этого Python-процесса и запустите выборку `ps`:

```sh
ps -eo pid=,comm=,args= | awk '$2 ~ /^python/ && $0 ~ /labs[.]lab2[.]receiver/ {print}'
./scripts/lab2_sample_processes.sh 12345 receiver_ps.csv
```

На передатчике запустите отправку на переднем плане, а во втором терминале передатчика — выборку `ps`:

```sh
# Терминал с отправителем:
python3 -m labs.lab2.sender <IP_ПРИЁМНИКА> reference.mp4 --port 5000 --fps 25 --width 1280 --height 720 --loop > sender.log 2>&1
```

```sh
# Второй терминал передатчика:
ps -eo pid=,comm=,args= | awk '$2 ~ /^python/ && $0 ~ /labs[.]lab2[.]sender/ {print}'
./scripts/lab2_sample_processes.sh 12345 sender_ps.csv
```

В обеих командах выборки замените пример `12345` на PID из строки `ps` для соответствующего Python-процесса. Дайте передаче идти **не меньше 300 секунд**. Остановите отправитель клавишами Ctrl-C в его терминале, затем так же остановите приёмник. Скрипты выборки завершатся после остановки соответствующих процессов. В обоих журналах должна появиться итоговая строка `SESSION`.

Остановите `tcpdump` клавишами Ctrl-C. Сохранённый файл проверьте командой `ffprobe -v error -count_frames -show_entries stream=nb_read_frames -of default=noprint_wrappers=1 received.h264`. Текущий показатель `cpu_s` в журнале приложения измеряет только Python-процесс; CSV-файлы содержат отдельные измерения Python и его дочернего FFmpeg.

## Измерения по пункту 5.5

Скопируйте `sender.log` и `sender_ps.csv` с передатчика в корень проекта на приёмнике, где уже находятся `receiver.log`, `receiver_ps.csv` и `lab2.pcap`. Из корня проекта запустите:

```sh
./scripts/lab2_report.sh sender.log receiver.log sender_ps.csv receiver_ps.csv lab2.pcap 5000
```

Скрипт выводит частоту сформированных и восстановленных AU, полезную скорость H.264 на обоих узлах, число отправленных и принятых UDP-пакетов, оценку потерянных пакетов и число неполных AU. `tshark` читает захват Wireshark и сообщает количество UDP-пакетов, IPv4-фрагментов и максимальную длину IPv4-пакета. `ps` собирает раз в секунду `%CPU` и RSS-память Python и дочернего FFmpeg; итог показывает среднюю сумму показаний `%CPU` и максимальную сумму RSS. Значение `%CPU` у `ps` усреднено за время жизни процесса; RSS двух процессов может учитывать общие страницы памяти дважды.

Счётчик `UDP_received` и количество UDP-пакетов в захвате включают контрольные пакеты. `UDP_missing_estimate` — оценка пропусков по номерам УПВ-1, а не точное измерение потерь на конкретном участке сети. Для сопоставления числа отправленных и дошедших пакетов сохраните захваты на обоих Ethernet-интерфейсах Orange Pi.

На приёмнике проверьте захват:

```sh
tshark -r lab2.pcap -Y 'ip.flags.mf == 1 || ip.frag_offset > 0' -T fields -e frame.number
tshark -r lab2.pcap -Y 'rtp || rtsp' -T fields -e frame.number
tshark -r lab2.pcap -Y 'udp.port == 5000' -T fields -e ip.len -e udp.length
```

Первые две команды должны вернуть пустой список. Максимальная длина приложения УПВ-1 — 1400 байт; при обычных заголовках ожидается IP-пакет не длиннее 1428 байт. Убедитесь, что фактический MTU позволяет такую длину. В Wireshark проверьте, что UDP payload начинается с `55 50` (`UP`) и содержит собственный заголовок УПВ-1.

## Восстановление Ethernet

Не перезапуская приложения, отсоедините Ethernet-кабель или отключите удалённый узел, затем восстановите. В журнале передатчика должны появиться события `ПРОВОДНОЙ_КАНАЛ_ПОТЕРЯН` и `ПРОВОДНОЙ_КАНАЛ_ДОСТУПЕН`; проверка доступности использует контрольные UDP-пакеты и ACK. После восстановления проверьте рост счётчиков AU на обоих узлах. Если во время разрыва потеряны H.264 единицы, декодер может восстановить изображение после следующего IDR.

## Что включить в отчёт

Схему сети с адресами, фактические команды и параметры, SHA-256 файлового опыта, таблицу частот и скоростей видео, счётчики потерь/неполных AU, CPU и RAM, фрагмент захвата с разбором Ethernet/IPv4/UDP/УПВ-1, результат отключения и восстановления связи. Не подменяйте измерения расчётными значениями.
