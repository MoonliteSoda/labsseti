# Лабораторные работы: передача визуальной информации

Исходный код разделён по лабораторным работам. Общие компоненты добавляйте в `src/labs/common`, а реализации и протоколы конкретной работы — в её собственный пакет.

## Структура

```text
src/labs/
├── lab2/   H.264 по Ethernet, протокол УПВ-1
├── lab3/   изображения по LoRa, протокол УРВ-1
└── lab4/   автомат состояний Ethernet + LoRa
```

Методические указания остаются в корне проекта. [Теория и схема передачи ЛР-2](THEORY_LAB2.md) объясняет H.264, AU, УПВ-1 и UDP. [Подготовка стенда](STAND.md) содержит порядок запуска и измерений. Список недостатков ЛР-2 и непроверенных требований — в [TASKS.md](TASKS.md). Папки ЛР-3 и ЛР-4 содержат краткие спецификации; реализации этих работ ещё предстоит добавить.

## Лабораторная работа №2

Нужен FFmpeg с кодировщиком `libx264`. Запустите приёмник на Orange Pi-получателе:

```sh
uv run python -m labs.lab2.receiver --host 0.0.0.0 --port 5000 --output received.h264 --decode
```

Затем запустите отправитель на Orange Pi-передатчике, подставив адрес получателя и файл:

```sh
uv run python -m labs.lab2.sender 192.168.1.20 sample.mp4 --port 5000 --fps 25 --width 1280 --height 720
```

Для циклической передачи короткого видео добавьте `--loop`. Отправитель получает поток FFmpeg постепенно, выделяет access unit по AUD (эквивалент границы `alignment=au`) и передаёт фрагменты УПВ-1 по UDP. Приёмник упорядочивает access unit, записывает только полные единицы в Annex-B файл и при `--decode` сразу подаёт их в FFmpeg-декодер. Для дополнительной проверки сохранённого файла:

```sh
ffmpeg -i received.h264 -f null -
```

При пропуске access unit приёмник ждёт `--assembly-timeout`, затем продолжает с ближайшей полной единицы. Отправитель периодически проверяет доступность приёмника контрольными UDP-пакетами и продолжает работу при ошибке отправки. Физическое отключение Ethernet и восстановление связи ещё нужно испытать на стенде; это отмечено в [TASKS.md](TASKS.md).

### Проверка передачи файла

Режим `lab2-filecheck` передаёт произвольный файл по UDP с подтверждением каждого блока и повтором при тайм-ауте. Приёмник подтверждает сохранённый блок; повторно пришедший блок подтверждается заново, но второй раз в файл не записывается. После передачи сравните SHA-256:

```sh
uv run python -m labs.lab2.receiver --port 5000 --output restored.bin
uv run python -m labs.lab2.filecheck 192.168.1.20 source.bin --port 5000
sha256sum source.bin restored.bin
```

Файловый режим использует stop-and-wait ARQ, поэтому восстанавливает потерянные блоки и сохраняет их порядок ценой меньшей скорости. Для H.264-видеопотока подтверждения и повторы не включены: видеоданные остаются UDP-потоком реального времени.

### Локальный тест протокола

```sh
uv run python -m unittest discover -s tests -p 'test_protocol.py' -v
```

Тест упаковывает двоичные данные в несколько пакетов УПВ-1, разбирает их в обратном порядке, собирает по номеру фрагмента и сравнивает SHA-256 исходных и восстановленных данных. Отдельно проверяется отклонение пакета с повреждённой полезной нагрузкой. Этот тест проверяет протокол в памяти; сетевую передачу файла проверяйте командами выше.

## Стендовые проверки

Для отчёта нужны пятиминутная передача, испытание отключения/восстановления Ethernet и захват `tcpdump`/Wireshark. Ограничение УПВ-1 в 1400 байт рассчитано на отсутствие IPv4-фрагментации при MTU 1500, но это предположение требуется подтвердить захватом на используемом интерфейсе. Также по захвату нужно убедиться, что нет RTP/RTSP и других готовых видеотранспортов. Результаты стенда не входят в локально проверенные свойства.
